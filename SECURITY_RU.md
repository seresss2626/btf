# Безопасность (протокол v5)

[English version](SECURITY.md)

Этот документ описывает, от чего защищает туннель начиная с v5, как это устроено, и что остаётся на вашей стороне.

## Что было не так в v4

| # | Проблема v4 | Последствие |
|---|---|---|
| 1 | Cloud Function проверяла токен только в `HELLO`. `PING`/`SYNC` и stream-кадры обрабатывались для **любого** WebSocket-соединения. | Любой, кто знал URL шлюза, получал **IAM-токен сервисного аккаунта** и connection ID адаптера одним кадром `PING` — и мог открывать TCP-соединения к вашему `target` (бесплатный открытый прокси за ваш счёт). |
| 2 | `CONNECT` на `/_adapter` без проверок записывал `adapterConnId = connId`. | Кто угодно мог занять место адаптера и получать трафик ваших хелперов (или просто положить туннель). |
| 3 | `DISCONNECT` любого соединения на `/_adapter` рассылал `PEER_GONE` всем хелперам. | Удалённый DoS одним connect/disconnect. |
| 4 | Адаптер и хелпер принимали любые кадры, пришедшие в их WebSocket. | Обладатель IAM-токена (см. п.1) мог через `wsSend` вбрасывать `OPEN`/`DATA`/`PEER_GONE` напрямую. |
| 5 | `/conn-ids` принимал `Bearer <authToken>`, а функция отправляла туда IAM-токен в заголовке — часто по голому HTTP. | Утечка общего секрета и IAM-токена любому, кто видит трафик до VPS; подмена ответа (фальшивый `adapterConnId`). |
| 6 | Без `AUTH_TOKEN` функция сравнивала токен со строкой `"undefined"`. | Туннель без пароля при ошибке конфигурации. |
| 7 | Полезная нагрузка шла в открытом виде через функцию/шлюз. | Облачный провайдер видел содержимое трафика. |

## Как устроено в v5

Секреты:

* **`authToken`** — общий для функции, адаптера и хелперов (в функции — env `AUTH_TOKEN`). Не короче 16 символов.
* **`e2eKey`** — общий **только** для адаптера и хелперов. В функцию **никогда** не передаётся. Необязателен, но настоятельно рекомендуется.

Из секретов через HMAC-SHA256 выводятся отдельные ключи для каждой задачи (см. `adapter-and-helper/internal/secure/secure.go`; реализации на JS и C# сверяются с ним по общим тест-векторам `testdata/vectors.json`).

1. **HELLO** содержит HMAC над отметкой времени и ролью (`adapter`/`helper`), а не сам секрет. Окно допустимой разницы часов — 5 минут. Неверный HELLO → `HELLO_ERR` и принудительное закрытие соединения.
2. **Тикет соединения.** Каждое последующее сообщение клиента в функцию заканчивается 16-байтным тикетом `HMAC(роль, connectionId)`. `connectionId` подставляет сам API Gateway, подделать его нельзя, поэтому тикет бесполезен на любом другом соединении. Сообщения без валидного тикета отбрасываются, соединение закрывается. Функция больше **не меняет состояние** (слот адаптера, список хелперов) по неаутентифицированным сообщениям.
3. **Подпись кадров функции.** Всё, что функция отправляет клиенту (`HELLO_OK`, `PONG`, `PEER_CONN`, `PEER_GONE`, а также `OPEN_FAIL`/`RST` в relay-режиме), подписано и привязано к connection ID получателя. Клиенты отбрасывают всё неподписанное — IAM-токен больше не позволяет вбрасывать управляющие кадры.
4. **Stream-кадры между хелпером и адаптером** всегда зашифрованы и аутентифицированы (AES-256-CTR + HMAC-SHA256, направление кадра входит в MAC — отражённые кадры не принимаются). Заголовок (тип, stream ID, seq) остаётся открытым для маршрутизации в relay-режиме, но защищён MAC. Ключ — из `e2eKey`, а если он не задан, из `authToken` (тогда функция теоретически может расшифровать трафик — поэтому задайте `e2eKey`).
5. **`/conn-ids`**: запрос подписан HMAC с отметкой времени (секрет по сети не передаётся), ответ подписан, IAM-токен больше не передаётся. Без валидной подписи эндпоинт отвечает `404`. Даже по HTTP ни секрет, ни токен не утекают, а подмена ответа не проходит.
6. **Проверка конфигурации**: слишком короткие секреты, `e2eKey == authToken`, `ws://` к нелокальному хосту, пустой `AUTH_TOKEN` в функции — ошибка запуска. Отсутствующие параметры переподключения получают безопасные значения по умолчанию.
7. **MAUI-клиент** хранит `authToken` и `e2eKey` в системном хранилище секретов (`SecureStorage`: Keychain / Android Keystore / DPAPI); значения из старых версий переносятся автоматически. На платформах без `SecureStorage` (Linux GTK) — прежний `Preferences`.

## Что остаётся на вашей стороне

* **Сгенерируйте секреты** случайно: `openssl rand -hex 32` (два разных — для `authToken` и `e2eKey`).
* **Задайте `e2eKey`** на адаптере и всех хелперах. Без него у функции (а значит, у облачного провайдера) есть ключ от трафика.
* **Сервисный аккаунт.** IAM-токен функции по-прежнему выдаётся аутентифицированным адаптеру и хелперам (без него не работает прямой `wsSend`). Держите мост в **отдельном каталоге** облака, где нет ничего, кроме этой функции и шлюза, и не выдавайте аккаунту других ролей.
* **Внутри туннеля** используйте протокол с собственной аутентификацией (VLESS/Xray, Shadowsocks, SOCKS с паролем). Все хелперы с правильными секретами полностью доверенные: они делят одни ключи и могут открывать соединения к вашему `target`.
* **Хелпер слушает только loopback** (`127.x.x.x`) — иначе вашим туннелем может воспользоваться любой в локальной сети (Go-хелпер предупреждает о нелокальном адресе).
* **Экспорт конфигурации в MAUI** (`btf://…`) содержит оба секрета — пересылайте только по приватному каналу.
* **Часы** на устройствах должны быть синхронизированы (±5 минут), иначе `HELLO` отклоняется с причиной `clock skew`.

## Известные остаточные риски

* Кто может расшифровать TLS до API Gateway (или сам провайдер), может в течение 5 минут переиграть перехваченный `HELLO` и получить IAM-токен. Провайдер его и так выдаёт; для прочих это требует взлома TLS.
* Объём и тайминги трафика, connection ID и заголовки кадров видны провайдеру — шифрование скрывает содержимое, но не факт использования туннеля.
* Хелперы доверяют друг другу (общие ключи): хелпер с валидными секретами может помешать потокам другого хелпера.

## Проверка

```bash
# Go: тест-векторы и отказ на подделанные/отражённые кадры
cd adapter-and-helper && go test ./...
# Функция: векторы + атаки из v4 (утечка токена, открытый прокси, захват слота адаптера, …)
node --test tests/cloud-function.test.js
# C# (сервисы MAUI-клиента): векторы
dotnet run -c Release --project tests/maui-services
# Полный локальный прогон: симулятор API Gateway + настоящие функция, адаптер,
# хелперы (прямой, relay, с неверным e2eKey) и MAUI-сервисы, с атаками
(cd tests/e2e && npm install) && SIM_INSTANCES=3 tests/e2e/run.sh
```
